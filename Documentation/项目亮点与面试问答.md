## 最值得讲的三个亮点

### 1. 状态机不只是枚举加 switch

每个状态实现统一生命周期，FSM 上下文只负责注册、更新和转换。状态之间通过共享参数交互，`StateGuards` 统一处理追击边界。这样新增“眩晕”或“返回出生点”等状态时，不必修改一个越来越大的 `Update`。

### 2. 打击感是一条协作链

玩家攻击动画控制攻击窗口；碰撞确认命中后，敌人进入受击、获得方向性击退，同时触发实时顿帧与二维摄像机震动。这里需要区分缩放时间和真实时间，否则 `timeScale = 0` 时普通协程计时会停住。

### 3. 能处理真实工程事故

原工程丢失后，从 Mono 程序集恢复脚本，从构建资源恢复场景/动画线索，再通过独立编译验证语法和依赖。随后进行来源审计，没有把第三方素材误包装为原创，也没有把无明确授权的资源重新上传。

## HR 常见问题与回答

### Q1：这个项目你独立完成了哪些部分？

我在一个 FSM 教学 Demo 的基础上完成横版游戏功能扩展，包括三段连击和攻击位移、顿帧与震屏、玩家/敌人生命和击退、关卡出口、宝箱、告示牌、菜单及 UI。当前仓库还对 FSM 做了结构化改写和缺陷修复。美术素材不是我原创，来源已经单独标注。

### Q2：为什么仓库不是完整可运行项目？

原 Unity 工程遗失，只保留了 Windows 构建。我从构建中恢复了代码和资源映射，但部分素材禁止作为素材包再分发，另一些没有明确许可证。因此公开仓库选择展示可审阅代码、恢复过程和匹配证据，不冒险上传第三方资源。

### Q3：你遇到的最难问题是什么？

难点不是反编译本身，而是区分“能够恢复”与“能够公开”。我用 Mono 程序集恢复业务逻辑，用 Unity 资源导出对比同名、尺寸和解码像素，确认 81 张素材来源；同时比较参考包脚本，重新界定了教学代码与自己的扩展代码。

### Q4：你修复了哪些实际 Bug？

包括怪物生命判断方向写反、玩家受击条件导致不扣血、FSM 同帧多次转换、初始 Animator 空引用、死亡每帧重复销毁、摄像机 Z 坐标错误、字符串比较 Collider 类型和全局攻击键误伤全部敌人等。

### Q5：为什么选择状态模式？

敌人行为具有清晰的互斥阶段，而且每个阶段都有进入、持续和退出逻辑。状态模式能隔离这些逻辑并降低新增行为的影响范围。小型敌人仍可用简单 switch，复杂度达到多个动画和转换条件时再使用状态对象更合适。

## 技术面常见追问

### Q：`Time.timeScale = 0` 后协程为什么还能恢复？

使用 `WaitForSecondsRealtime`，它基于未缩放时间；摄像机震动也使用 `Time.unscaledDeltaTime`。如果使用 `WaitForSeconds` 或 `Time.deltaTime`，暂停期间计时会停止。

### Q：如何避免同一帧连续切换多个状态？

高优先级转换（如受击、死亡）执行后立即 `return`。FSM 还会拒绝切换到当前状态，保证一次更新只产生一个有效转换。

### Q：为什么保留拼错的 `CamreaFollow` 类名？

Unity 场景和 MonoBehaviour 脚本引用依赖类型/脚本资产关联。恢复阶段直接改名可能让已有序列化引用失效，所以保留兼容类名，在注释中解释；若有完整工程，可通过 Unity 编辑器迁移组件后再重命名。
